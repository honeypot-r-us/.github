# Testing and repository automation: Rust-first

All new or modified repository **test harnesses, contract/CI validation scripts, schema/code-generation checkers, mutation tests, fixtures validators, and automated gate utilities** for `honeypot-r-us` and `honeypot-r-us-test` must use **Rust rather than Python**. Favor Rust integration tests in an existing Cargo crate, `cargo test --locked`, and small Rust CLIs for deterministic artifact generation and drift checks. Run `cargo fmt --all -- --check` and `cargo clippy --all-targets --locked -- -D warnings` on affected Rust code. Validation must be fail-closed with explicit positive and negative tests; missing tools, skipped tests and unavailable CI are not evidence of success.

When a change touches an existing Python testing utility, migrate that utility and its workflow call sites to Rust, remove dead Python testing entrypoints and document any remaining test migration debt. Do not introduce new Python-based CI checks. This policy does **not** remove the existing Python client-language SDK lane, or forbid executing target-language compiler checks for shipped code (e.g., Dart, TypeScript and Go). Third-party/upstream tooling or a production Python component may remain when needed; don't confuse that with authoring our testing logic in Python.

Keep source and test organizations aligned. For private/cross-org CI, avoid personal access tokens: use reviewed exact-commit snapshots with Git blob SHA provenance or a token-free mirror into an authorized runner organization, and require actual execution receipts before promoting to production. Tests must never log secrets. Security review and existing repository protections still apply; do not merge draft or failing PRs.
